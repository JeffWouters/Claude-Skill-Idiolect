## The passage (by the author)

What might it mean to take the wish seriously without simply obeying it? It seems to me that a more honest conversation might begin by naming what the rewrite is meant to relieve—the embarrassment of a confusing design, the weariness of long maintenance, the suspicion that careful repair will go unnoticed. Some of those burdens could be eased without discarding anything; a team might, for instance, set aside time to rename, to delete and to explain, and might treat the patient improvement of an inherited system as work worth describing in the same terms as a launch. None of this requires a new methodology or a new set of tools, only a willingness to look at the old system as something we are responsible for rather than something that happened to us. It is slower and considerably less exciting, and it offers none of the clean satisfaction of a fresh beginning; I suspect that is precisely why it is so rarely proposed.

The rewrite, like so many ambitions of working life, is in some sense a hope about ourselves rather than about the system. We imagine that on the other side of it we will be more careful and more deliberate than the people who came before us, and we are usually wrong in the gentlest possible way, since the same deadlines and the same partial knowledge will be waiting for us too. There is something quietly humbling in recognising this—the old code was written by people much like us, under conditions much like ours, doing what they could. Perhaps the real temptation is not to start again but to believe that starting again would make us different people. Perhaps the braver thing, and the kinder one, is to stay with what we have inherited and leave it a little better than we found it.

## Draft A

When engineers say that a legacy system ought to be rewritten, it is tempting either to agree or to refuse, and it seems to me that neither response takes the request quite seriously enough. The proposal is usually a summary of frustrations rather than a plan, and the more useful question is what those frustrations are. Some of them can be eased far more cheaply than a rewrite would allow: a module whose name no longer describes what it does can be renamed; code that nobody calls can be deleted; behaviour that everyone has to rediscover can at last be documented. None of this is glamorous, which is perhaps why it so rarely happens, and it will only happen if incremental improvement is treated as real work, noticed and valued, rather than as something done in the margins of the work that counts.

There is also, I suspect, something more personal in the wish to start again. A rewrite promises not only a better system but a better version of ourselves, the engineers we might have been had we been given a clean page and enough time. The difficulty is that the pressures which shaped the old system—the deadlines, the shifting requirements, the compromises nobody quite chose—do not disappear when we begin anew, and they tend to reassert themselves long before the new system is finished. It may help to remember that the people who wrote the code we now resent were working under much the same limits, and were very probably no less capable than we are. Improving what we have inherited, patiently and in place, is rather less satisfying than building something fresh. It is also, more often than we would like to admit, the wiser course.

## Draft B

When engineers say that a legacy system needs to be rewritten, the most useful response is rarely to agree or to refuse, but to ask what, specifically, is making the work so painful. The answers tend to be concrete once they are drawn out: names that no longer describe what the code does, modules that nobody dares remove, behaviour that exists only in the memory of someone who has since left. Many of these frustrations can be addressed without starting again. Things can be renamed; dead code can be deleted; the reasoning behind a strange decision can be written down while someone still remembers it. None of this happens, though, unless the team treats such incremental work as genuinely valuable rather than as a consolation prize for having been denied the rewrite.

It is worth acknowledging what the wish for a rewrite often expresses. Beneath the technical argument there is frequently a hope—entirely sympathetic—that this time we will do things properly, that a clean start will allow us to become the engineers we would like to be. The difficulty is that the pressures which shaped the old system have not gone anywhere. The deadlines, the shifting requirements, the compromises made under uncertainty will all return, and they will leave their marks on the new code much as they did on the old.

Perhaps the more generous way to regard a legacy system is as the work of people who faced much the same constraints we face now, and who made the choices that seemed reasonable at the time. Seen in that light, the question is less whether we could do better from scratch than whether we can do better with what we have been given. Improving inherited code is slower and less glamorous than replacing it. It is also, in most cases, the wiser course—and it has the considerable advantage of being something we can begin tomorrow.

## Draft C

What should we say when an engineer proposes to rewrite a legacy system from scratch? The instinct of most managers is to argue about cost and risk, and these arguments are sound as far as they go, but they rarely persuade, because the proposal is seldom really about the system. It may be that the more useful response is to ask which particular frustrations lie behind it, and then to ease them one at a time: by renaming what is misleadingly named, by deleting what nobody uses, by documenting what nobody understands, and by treating incremental improvement as work worth recognising rather than as maintenance to be tolerated.

There is also something more personal in the wish to start again. A rewrite carries the hope of becoming a better engineer, of finally building the thing properly, without the compromises that seem to disfigure the existing code. I suspect this hope is sincere, and I suspect it is also misplaced, since the pressures that shaped the old system—deadlines, shifting requirements, incomplete knowledge—have not gone anywhere; they will return in time, and the new system will begin to acquire the same compromises for the same reasons.

It seems to me that the most helpful thing to remember is that the earlier authors were rarely careless. They worked under limits much like our own, and many of the decisions that now look strange were reasonable given what they knew at the time. Improving the code we have inherited is less glamorous than replacing it, and it offers no clean beginning; it is, I think, considerably more likely to leave the system better than we found it. Perhaps the wiser ambition is not to write the code our predecessors should have written but to become the predecessors our successors will be glad to have had.

## Draft D

Sooner or later, an engineer on a team that maintains a legacy system will say it: we should rewrite this. The urge is understandable, and dismissing it outright rarely helps. A better answer starts by asking what is behind it.

Usually there is a set of concrete frustrations. The names in the code no longer match what things do. Whole sections are dead but nobody dares remove them. Nobody remembers why a particular decision was made, so every change feels risky. And the slow work of improving the system bit by bit earns little recognition compared with shipping something new. Each of these can be eased without starting over. Rename what is misleading. Delete what is unused. Document the decisions that people keep tripping over. And make it clear, in how work is planned and praised, that incremental improvement counts.

It also helps to understand what a rewrite represents. It is rarely just a technical proposal. It carries a hope: that with a clean slate, this time, we will be the engineers we want to be, making the right choices from the start. That hope is worth taking seriously. But the pressures that shaped the old system do not disappear because the code does. Deadlines, changing requirements, partial knowledge and competing priorities will all return, and they will shape the new system too.

The people who wrote the original code were working under similar limits. They were not careless; they were making reasonable choices with what they had at the time. Seeing them that way changes the conversation. The legacy system stops being a mistake to escape and becomes a record of constraints that still apply.

None of this means a rewrite is never right. But improving inherited code is often the wiser path, and it keeps what the system has already learned.
